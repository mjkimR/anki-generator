# TTS Engine Selection: Reading Accuracy vs. Naturalness

- Status: Open — Polly shipped as a selectable provider and is on live trial; the default
  provider stays `azure` until the trial decides it
- Date: 2026-08-04 (updated 2026-08-13)
- Related: [ADR-0010](decisions/0010-explicit-fail-closed-tts-provider.md) (Azure default, fail-closed),
  [ADR-0013](decisions/0013-aivis-reading-verification.md) (Aivis verify-first)

## Problem

ADR-0013 assumed that what `audio_query` reports is what `/synthesis` speaks. A live
card broke that assumption: in 技術革新の恩恵を享受できるのは、一部の層に限られる。 the
query reports 層に as ソウニ (correct, verification passes), but the synthesized audio
articulates something closer to サダニ. Pitch-scale changes do not fix it; rewriting the
word as katakana in the input text does.

The mechanism is architectural, not a pipeline bug. AivisSpeech Engine is an end-to-end
Style-Bert-VITS2 model behind a VOICEVOX-compatible API, and its README documents the
relevant differences:

- The reading fed to synthesis comes from the accent-phrase mora `text` values (this is
  why the ADR-0013 dictionary ladder works), but `AudioQuery.kana` is repurposed to
  carry the **original kanji sentence**, which conditions the acoustic model (BERT text
  features).
- Mora `consonant`/`vowel` fields are read-only, and per-mora pitch/length are
  unsupported dummy values — prosody and articulation are generated by the model.

So the phoneme sequence is an input, not a guarantee: when the kanji-text conditioning
disagrees with the verified moras, the model can articulate away from the reading the
pipeline verified. Katakana input fixes such words because both channels then agree.
The official guidance for this failure mode is "regenerate and pick," i.e. the vendor
acknowledges it as a model characteristic.

**Consequences for the pipeline:**

- ADR-0013's "no wrong audio ships" guarantee actually covers the engine's *analysis*,
  not its *acoustics*. `check-readings` cannot detect this class in principle.
- Detection currently requires listening. A "found by ear → register a quirk" loop was
  considered and rejected: its cost scales with deck size and never converges.
- Known incidence: 1 card out of ~388. The true rate is unknown *because* nobody has
  listened to everything — which is exactly the trust problem.

## What each current provider guarantees

| | Azure (`azure-ssml-v2`) | Aivis (`aivis-dict-v1`) | Polly (`polly-yomigana-v1`, added 2026-08-13) |
| --- | --- | --- | --- |
| Reading accuracy | **By construction** — every bracket word is replaced with `<sub alias="カタカナ">`, so the validated furigana *is* the pronunciation | Verified at analysis level only; articulation unverifiable without listening | **By construction** — `<phoneme alphabet="x-amazon-yomigana">` forces the reading while leaving the word in the text |
| Naturalness | Noticeably awkward: alias substitution discards the surface word, chopping intonation and inter-phrase pause timing | Natural prosody (kanji context conditioning) — the reason Aivis was adopted | The word survives, so the front end keeps its context; on trial |
| Ops | Cloud key (push machine only), negligible cost | Local engine, free | AWS credentials (push machine only), negligible cost |

This is the trade: **accuracy vs. naturalness**. The interim position is Azure
(accuracy wins until a better option is validated).

## Decision plan

1. Ear-test the two surviving candidates below against Azure and Aivis renders of the
   same sentences.
2. If VOICEVOX passes the ear: adopt it (structural fix, near-config port).
3. Else if Polly is less awkward than Azure: adopt Polly (accuracy by construction with
   a less destructive injection mechanism).
4. Else: keep Azure for now and design an ASR back-check gate to make Aivis (or any
   natural-text mode) verifiable at the audio level. Aivis returns only behind that gate.

The pending 362-card audio backfill is **gated on this decision** (an Aivis backfill
would mass-produce acoustically unverified audio; a cloud-provider backfill removes the
GPU-machine dependency entirely).

### Progress (2026-08-13)

The Appendix B samples were synthesized on the AWS console and Polly cleared the bar the
ear test was for, so it now exists as a real provider: `TTS_PROVIDER=polly`, voice
`Tomoko`, renderer `polly-yomigana-v1`
(`tts_helper/providers/polly.py`). Nothing about the default changed — `azure` remains
`config.TTS_PROVIDER`'s default, and this document stays open — because the decision the
samples support is "worth using for real", not yet "worth committing the deck to". What
closes it is living with Polly audio on actual review sessions.

When it closes:

- Adopted → flip the default in `config.py`, write the ADR superseding
  [ADR-0010](decisions/0010-explicit-fail-closed-tts-provider.md)'s provider clause, and
  run the gated backfill (which also ends the Aivis GPU-machine dependency).
- Rejected → the fallback ladder below is unchanged; Azure keeps shipping audio and the
  ASR back-check gate becomes the next design question.

Whichever engine ships audio, `check-readings` keeps its value as a *furigana linter*
(it caught 通[とお]じて → つうじて); that role ships no audio and is immune to the
articulation gap.

## Candidate survey

### Candidate 1 — Amazon Polly neural + `x-amazon-yomigana` (cloud)

Polly has a Japanese-specific reading-injection mechanism that, unlike `<sub>`, keeps
the surface word in the text and annotates it with its reading — the SSML equivalent of
furigana:

```xml
名前は<phoneme alphabet="x-amazon-yomigana" ph="ひろかず">浩一</phoneme>です。
名前は<phoneme alphabet="x-amazon-pron-kana" ph="ヒロ'カズ">浩一</phoneme>です。
```

- `<phoneme>` is **Full availability on the neural engine** (confirmed in the supported
  tags table). `x-amazon-pron-kana` can even pin the pitch-accent nucleus (apostrophe) —
  unused for now (cards carry no accent data) but a real extension path.
- Readings are forced by construction, like Azure, but the front end keeps the original
  word for context, so the prosody chopping that makes Azure awkward may not apply.
  Whether it actually sounds better is the ear test's question.
- ja-JP neural voices: Kazuha, Tomoko (F), Takumi (M). Cost class same as Azure
  (negligible at this deck size). Requires an AWS account (signup pending).
- Implementation if adopted: a `PollyTTSProvider` the size of `azure.py` — the
  `prepare_text` transform emits `<phoneme>` instead of `<sub>`.

### Candidate 2 — VOICEVOX (local)

The engine Aivis forked its API from, with the opposite architecture at the exact point
that matters: synthesis **consumes the AudioQuery moras, pitch, and length as hard
inputs** (the GUI exposes per-mora pitch editing — those fields are live, not dummies).
"What `audio_query` shows is what you hear" holds as a contract, so the articulation
gap does not exist structurally.

- API-compatible with the existing provider: the ADR-0013 ladder, user-dictionary
  escalation, and `check-readings` port almost as configuration (different port/speaker,
  bump `render_version`).
- Free, local, no keys. The only open question is **voice quality**: VOICEVOX timbre is
  more synthetic/character-styled than Style-Bert-VITS2. Only the ear can rule.

### Rejected without testing

| Engine | Reason |
| --- | --- |
| Aivis Cloud API | Same Style-Bert-VITS2 family → same articulation gap; no gain on the trust axis |
| Google Cloud TTS | Reading control is the same `<sub>` mechanism as Azure (same awkwardness class); newest Chirp3-HD voices accept no SSML at all |
| ElevenLabs / OpenAI TTS | Top naturalness but effectively no Japanese reading control — a stronger version of the "trust and listen" model this issue exists to eliminate |
| CoeFont / にじボイス | High quality but API-level reading/accent control unconfirmed, subscription pricing; revisit only if both candidates fail |
| Kokoro-class open phoneme-driven models | Readings forceable but mid-grade Japanese pitch accent and fully DIY ops |

## Ear-test protocol

Synthesize the 8 sentences below with each candidate and compare against the current
Azure renders and the Aivis renders of the same cards.

| # | Sentence (target) | Why it is in the set |
| --- | --- | --- |
| 1 | 技術革新の恩恵を享受できるのは、一部の層に限られる。(享受) | The articulation-gap witness: 層に must sound ソウニ |
| 2 | 「最近弛んでいるぞ」と監督に叱られ、部員たちは慌てて背筋を伸ばした。(弛む) | Dictionary-resistant reading (Aivis needed the okurigana-prefix stage); quoted speech intonation |
| 3 | 次期経営計画では、顧客満足を戦略の中核に据える方針だ。(据える) | 顧客 was Aivis's one kana-substitution card |
| 4 | 締め切りまで余裕があり、彼は悠々と昼食をとっていた。(悠々) | Repetition-mark 々 handling |
| 5 | 終電に辛うじて間に合い、深夜の帰宅を免れた。(辛うじて) | Heteronym 辛 = かろ(うじて) |
| 6 | 今は辛くても、傷はじきに癒えるものだ。(じきに) | Heteronym pair: same surface 辛 = つら(くても) |
| 7 | 度重なる失敗にも挫けず、彼は新規事業の立て直しに挑み続けた。(挫ける) | Long multi-clause sentence — pause timing / intonation comparison |
| 8 | 粘り強い交渉の末、ようやく先方から契約更新の内諾を取り付けた。(取り付ける) | Long business sentence — the register most cards use |

Listen for, in order: (a) #1's 層に articulation; (b) heteronym correctness in #2/5/6;
(c) pause timing and phrase intonation on #7/8 versus Azure's current renders — this is
the axis Azure loses on today and the main thing Polly must beat.

**VOICEVOX**: install the desktop app (bundles the engine; serves the
VOICEVOX-compatible API on `127.0.0.1:50021` while running). Paste each sentence from
Appendix A into the GUI, confirm the displayed reading matches the furigana (a manual
`check-readings`), synthesize, listen. Sample a few adult/neutral voices; accuracy is
structural here, so judge naturalness only.

**Polly**: AWS console → Amazon Polly → Try Polly, SSML mode, Japanese, neural engine,
voices Kazuha / Tomoko / Takumi. Paste each block from Appendix B. Accuracy is forced;
judge naturalness, especially pause timing around the tagged words.
